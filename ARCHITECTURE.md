# Mango Pro — Architecture & Build Plan

## Context

Mango has three live products today — the site (`mango-bridge.jsx`), the mobile wallet (`mango-mobile`), and the Telegram bot (`mango-telegram-bot`) — all built around the same chain-first mental model: pick a source chain, pick a destination chain, pick an asset, then bridge/swap. "Mango Pro" (repo: `rhynox-ui/mango-pro`, currently empty) is a new, additive product built on the opposite premise: the user searches for a token by name/ticker, and the app figures out which chain it's on, how to pay for it, and how to route/bridge/execute automatically. It must stay non-custodial and, per the user's explicit priority, must not require the user to hold native gas on the destination chain — gas itself should disappear from the user's mental model, the same way the chain does.

Three research passes across all three sibling repos (routing/execution logic, wallet/security architecture, and service-layer/fee consistency) surfaced one concrete, already-realized risk worth designing around directly: the bot's fee-rate constant silently drifted to double the intended rate because chain/fee data is hand-copied across the three repos with no shared source of truth, and that bug was only caught and fixed today. Mango Pro's own internal data layer needs enough discipline that it doesn't repeat this on its own, even though — per the user's explicit steer — it will live inside this one repo rather than a separate shared package for now.

Three decisions below reflect the user's explicit choices (not just a default recommendation): Mango Pro gets its **own embedded smart-contract wallet** (not external-wallet-only) specifically so gas can be sponsored/abstracted away; the **UI should look and feel like mango-mobile**, adapted for a token-first flow; and the **chain/fee/routing logic is built inside this one repo**, carefully, rather than as a new separate package repo.

---

## 0. Competitive validation, and the build-vs-buy question — resolved

**This section originally posed a four-way, unresolved comparison (build on Pimlico vs. adopt Particle Universal Accounts vs. Alchemy vs. Biconomy) assuming a from-scratch ERC-4337 wallet.** That framing is now resolved, and the original premise (fresh ERC-4337 smart accounts) is superseded by §1 below — left here so the reasoning is on record, not silently dropped.

- **[FOMO](https://en.wikipedia.org/wiki/Fomo_(platform))** — a funded ($75M Series B, $550M valuation), shipping mobile-first multichain trading app — remains the closest real precedent: one balance spanning Solana/Base/BNB/Monad/Ethereum/Robinhood Chain, aggregated (not settlement-pinned, see §3a), with EVM gas sponsored via account abstraction. Confirmed directly against Relay's own docs that **Relay's Depository contract already works with plain EOAs today** (an EOA just signs `approve`+`depositErc20` as two transactions where a smart account can batch them into one) — so Relay was never the reason FOMO needed smart accounts. The actual gap smart accounts close is narrower and specific: **origin-chain gas**, the one thing Relay's own Fee Sponsorship (destination-only) never covers.
- **Particle Network's "Universal Accounts" is not a shortcut past building this — it's a different, redundant thing to build.** Confirmed directly from Particle's own whitepaper: Universal Accounts are "specialized ERC-4337 Smart Account implementations... coordinated across chains," with their own "Universal Liquidity" bridging layer underneath standing in for exactly what Relay already does for Mango Pro, tested and working. Adopting it would mean replacing already-functioning Relay integration with Particle's equivalent for no new capability — free pricing doesn't offset that redundancy. (Particle Auth, the separate social-login product used in §1's onboarding, is a different thing again — currently gated off for an unrelated reason, see §1's own note.)
- **Decision: Pimlico**, evaluated against Alchemy Gas Manager and Biconomy. Pimlico is pure bundler+paymaster plumbing (no opinionated wallet or routing layer to conflict with Relay), is viem-native via `permissionless.js` — matching Mango Pro's existing stack directly — and has a real free tier (250k sponsored UserOperations/month) to prove the integration before any spend commitment. Revisit **Biconomy** specifically once live across many EVM chains, for its unified-gas-tank model (one funded balance sponsoring every chain instead of managing a separate paymaster float per chain) — a real operational question once Mango Pro is live on 8+ EVM chains, not before.

## 1. Wallet: the real shipped foundation, plus EIP-7702 for gas sponsorship

**What's actually built today** (this section previously described a speculative browser-based, WebAuthn/passkey-gated design that was never built — Mango Pro is a bare React Native app, not a browser app, so that design doesn't apply and is removed here rather than left to mislead): a standard BIP-39/HD seed-phrase wallet, keys encrypted at rest the same way `mango-mobile/src/wallet/` already does (its OS-level secure storage, not a browser API), plus **Particle Auth** as a second onboarding path — Google/social login backed by MPC key-splitting, so no single party including Mango ever holds the whole key. Both paths are plain EOAs today. The seed-phrase path is the one live in the app right now — see the note directly below on why.

**Google login is built and real, but currently gated OFF, not removed.** A single flag, `GOOGLE_LOGIN_ENABLED = false` in `App.tsx`, withholds `onGoogleLogin` from `WelcomeScreen` (which then simply doesn't render the Google button or its divider — Create/Import are the only onboarding paths a user ever sees) and skips the cold-start attempt to restore a lingering Particle session. `DocumentationScreen.tsx` was rewritten to match — it no longer describes Google sign-in as something available, since a user reading it would otherwise hit an immediate, visible inconsistency. Why gated rather than shipped or deleted: the one real, confirmed gap is EIP-7702 gasless trading, which Particle's currently-exposed SDK surface cannot sign (see §1's own "Cost recovery" note and §1a's EVM writeup) — with real product priority on "full parity or don't offer it," gating was the lower-risk move over either shipping a visibly second-class login option or discarding working code. This was a safe, zero-impact decision specifically because Mango Pro is still pre-launch (dev/testing only, confirmed before acting) — deleting or hiding a login method after real users hold funds under it would risk stranding them, since a Particle session's key never touches this device at all. Everything downstream — `particleAuth.ts`, `particleSigning.ts`, the Solana fee-payer fallback and cost recovery built for it (§1a below), every `authMethod === 'google'` branch in trade execution, referrals, and settings — is untouched and fully functional; it simply never runs because no session can become `'google'` anymore. Re-enabling later is a one-line flip of that same flag, not a rebuild.

**The addition: EIP-7702, not a fresh ERC-4337 smart account.** The reason to prefer 7702 over deploying a brand-new counterfactual smart-account address: Mango Pro already has real users on real EOA addresses, and a fresh ERC-4337 account would mean a different address per user with a real migration story to solve. EIP-7702 (live since Ethereum's Pectra upgrade, ~14 million EOAs have already used one) instead lets an **existing EOA** temporarily delegate execution to a smart-contract implementation — same address, no redeploy, no "why did my address change." The same providers (Pimlico included) serve both standards through identical bundler/paymaster infrastructure, so this isn't a separate integration path.

Concretely, per EVM trade:
1. The user's existing wallet signs a 7702 delegation authorization (one-time, or re-signed per session).
2. Pimlico's bundler submits a UserOperation batching `approve`+`depositErc20` into Relay's real Depository contract as one signature — a real UX win beyond gas, since an EOA today needs two separate signatures for the same thing.
3. Pimlico's paymaster sponsors that UserOperation's gas — origin-chain gas requirement gone.
4. Everything downstream is already built and unchanged: Relay's solver fronts destination-chain liquidity, Relay's own Fee Sponsorship covers destination gas, and Solana-side sponsorship stays the already-planned backend fee-payer (§ below) — Solana never had this problem once that's wired in, since it needs no account-abstraction layer at all.

This ships as an **opt-in** "Enable gasless trading" toggle, not forced onto existing users — someone who doesn't opt in keeps trading exactly as today, holding native gas on whichever chain they spend from.

- **Solana doesn't need any of this.** Solana already supports a transaction **fee-payer field distinct from the signer** — Mango Pro's own backend can sponsor Solana transaction fees directly (a fraction of a cent per transaction, funded from the protocol fee already being collected), fully closing the "0 SOL" gap without any account-abstraction complexity. Solana side of the wallet stays a standard keypair, same derivation approach as EVM.
- **Non-custody is preserved throughout**: the 7702 delegation is signed by the user's own key, never something Mango holds or can act on unilaterally — the smart-contract implementation it delegates to is just executable code the user's own signature authorizes per action, not a new custody boundary.
- **Cost recovery, same contract as Solana's (§1a), adapted to this side's real mechanism.** Pimlico's paymaster here is billed against Mango's own funded Pimlico balance — a real cost, same category as Solana's fee-payer wallet spending real SOL, and one Relay's own `appFeeBpsForSponsoredTrade()` bps never actually covers (that bump only fires for Relay's OWN `subsidizeFees`/Solana-destination sponsorship — this Pimlico path is a separate, independently-toggled opt-in that was never wired into it at all). `sendRelayEvmStepSponsored` (`executeRelayQuote.ts`) closes that gap the same way as Solana: a 7702 smart account can batch multiple calls into ONE UserOperation, so a second call — an ERC-20 USDC transfer to the existing `DEV_FEE_WALLET` (already the appFees recipient; no new address to provision) — gets appended atomically alongside the swap, sized to this specific UserOperation's real worst-case gas cost (measured via `prepareUserOperation`, never guessed), live-priced against that chain's native asset, plus the same 1% non-profit conversion buffer. Genuinely different from Solana's single simulate-then-sign step: viem/permissionless splits "measure" (`prepareUserOperation`, no broadcast) from "send" (`sendTransaction`, broadcasts), so the shape here is prepare-to-measure the swap alone, decide, prepare-again as the real pre-flight on the combined calls, then exactly one broadcast — never a retry after something has already gone out. Any failure at either prepare step (paymaster policy rejects the extra call, no live price, insufficient USDC) falls straight back to the swap-only call, same "recovery is opportunistic, the trade succeeding never is" rule as Solana. Verified in `scripts/verify-evm-sponsorship-recovery.mjs` (the cost math and the chain-id lookup; the live prepare-then-decide flow around them needs a real bundler and isn't testable offline).

## 1a. Solana fee-payer sponsorship — shipped, plus a real firewall bug it exposed

§1 and §6 above describe this as "the already-planned backend fee-payer" — it's since been built, deployed, and (after a real, confirmed bug) fixed. Documented here rather than left as a forward reference.

**What's actually built.** `mango-api` (the shared Cloudflare Worker backend, not `mango-bridge.jsx`) exposes `GET /api/v1/solana/fee-payer` (returns the sponsor's public key) and `POST /api/v1/solana/sponsor-fee` (co-signs a transaction as fee payer). On the client, `executeRelayQuote.ts`'s `signAndSendSponsoredSolanaStep` rewrites any account-creation instruction's funding account to the sponsor (`rewriteAccountCreationFundingInstructions`, verified against real `@solana/web3.js`/`@solana/spl-token` output, not hand-crafted bytes) and follows the safe signing order confirmed against Alchemy's and Privy's own production implementations: the user signs first (locking the final message, including the funding-account rewrite), the sponsor signs last, only after verifying that user signature is already present. Relay's own documented `depositFeePayer` flow (sponsor signs first) is explicitly flagged by Relay's own docs as exploitable for same-chain Solana swaps — this app never uses that order. Real limits on the backend: deliberately just one now — the sponsor wallet's own on-chain SOL balance floor (`MIN_SPONSOR_BALANCE_LAMPORTS`, 0.01 SOL). A per-address 24h cooldown and a daily global cap both existed here too at first, but a real trade hitting the cooldown — "Fee sponsorship is limited to once every 24 hours per wallet" on an otherwise honest second trade — showed both added little real protection while blocking normal repeat trading; both removed on explicit product decision. Sponsorship now keeps covering trades until the fee payer wallet is genuinely out of SOL, with no other backstop — see "Cost recovery" below for how that wallet gets refilled instead of just spent down.

**Cost recovery.** Removing the rate limits above raised the obvious next question: is this sponsorship actually being paid for, or is it a straight giveaway? Real precedent (Solana-native relayer infra — Kora, Circle's Gas Station, Openfort — confirmed via their own docs) all recover cost the same way: an SPL-token transfer to the fee payer's own account, executed INSIDE the same transaction being sponsored, not a quote-time percentage bump computed ahead of time. `signAndSendSponsoredSolanaStep` implements exactly that, under one hard rule: **recovery is strictly opportunistic — it never gets to risk the trade it's protecting.**
- **Amount**: this specific transaction's real lamports cost (base network fee, plus any account rent this fee payer is now funding — read straight off the route's own instructions via `estimateSponsorshipLamportsCost`, never guessed), priced live against SOL/USD (`walletPrices.ts`, the same feed `fees.ts`'s own sponsorship-floor math already uses) so it tracks SOL's real volatility instead of a stale constant, plus a 1% buffer (`sponsorshipRecoveryUsdcUnits`) sized only to cover the eventual cost of converting this wallet's accumulated USDC back into SOL — not a profit margin. Recovering more than sponsorship actually cost would be exactly the "cheating" the flat `appFeeBpsForSponsoredTrade()` floor on the Relay-sponsorship side already exists to avoid; this mirrors that same discipline on the custom fee-payer side.
- **Never in the way of the trade**: recovery is paid in USDC from whatever the user's wallet already holds — deliberately NOT tied to this swap's own origin/destination currency, so a Buy and a Sell are handled identically with no special-casing. If the user doesn't hold enough USDC, or the augmented transaction fails to simulate clean for ANY reason, recovery is dropped entirely and the plain, already-proven sponsored transaction goes out instead. The trade succeeding is never conditional on recovery succeeding.
- **Compute budget, measured not guessed**: an added SPL transfer costs real compute units Relay's own route never budgeted for. The augmented instruction set is simulated client-side before signing (`sigVerify: false, replaceRecentBlockhash: true` — the same pattern `coSignAsFeePayer` already uses server-side); only on a clean simulation does its real `unitsConsumed` get used to correct (or add) a `SetComputeUnitLimit` instruction to 110% of that measured value (`withComputeUnitLimit` — replaces an existing one from Relay's own route rather than duplicating it, which the runtime would reject outright).
- The sponsor's own USDC associated token account is created lazily and idempotently the first time it's needed, funded by the fee payer's own signature for its own account — no user funds touched by that half of it.

**Google-login (Particle MPC) sessions get this too, via a different trigger than the local-key path.** A Google session has no local secret key, so `signAndSendRelaySolanaStepViaParticle` had no fallback at all until now — a low-SOL Google-login user's trade simply failed outright, a real gap a seed-phrase user never hit. Fixed by generalizing `signAndSendSponsoredSolanaStep` to take an abstract `SolanaTransactionSigner` (`{publicKey, sign}`) instead of a raw `Keypair` — the recovery/compute-budget logic above is identical either way, only "how does the user's signature get onto the message" differs. The trigger differs too, deliberately: the local-key path detects a shortfall by catching the RPC's `insufficient lamports X, need Y` text AFTER a submit attempt; Particle's `signAndSendTransaction` collapses sign-and-broadcast into one call with no confirmed guarantee its error surface preserves that same RPC text, so the Particle path instead checks BEFORE ever calling Particle — the same `estimateSponsorshipLamportsCost` math the recovery feature above already uses, compared against a real `getBalance()` read. Signing itself goes through `solana.signTransaction` (`particleSigning.ts`'s new `signSolanaTransactionViaParticle`) — a real, typed, sign-only primitive confirmed directly in the installed `@particle-network/rn-auth-core` SDK (distinct from the sign-and-broadcast `signAndSendTransaction` already used elsewhere), which is exactly what the safe signing order needs: get the user's signature onto the sponsor-funded, rewritten message WITHOUT broadcasting first. One piece is inferred rather than independently confirmed the same way this codebase's other Particle wire formats are: `signTransaction`'s return encoding is assumed to be base58 (matching every other Solana method in that SDK, per Particle's own docs already cited in `particleSigning.ts`), not proven against a real device — flagged there, not silently assumed safe, same discipline already applied to this file's other Particle functions.

**EVM gasless trading (§1's EIP-7702/Pimlico path) stays local-key-only — a deliberate, disclosed scope boundary, not an oversight.** Checked directly against the installed `@particle-network/rn-auth-core` SDK's real exported surface (`evm.d.ts`): `personalSign`, `signTypedData`, `sendTransaction`, `batchSendTransactions` — none of these can produce a valid EIP-7702 `SetCodeAuthorization` signature, which is neither a plain transaction nor standard EIP-712 typed data but a distinct raw-hash signature scheme this SDK exposes no primitive for. `executeRelayQuote.ts` already forces `useGaslessTrading` off for a Google session (`isGoogleSession` check in the main loop) — a Google-login user on EVM just pays their own gas normally, the same safe, already-proven fallback as anyone who hasn't opted into gasless trading, never attempted and never silently broken. One real, unresearched avenue worth flagging for later: `AAFeeMode.gasless()`/`.token()`, present in the installed SDK (`@particle-network/rn-base`'s own `AAFeeMode` model), hints Particle has its OWN native account-abstraction/paymaster product — a completely different integration from the Pimlico one this app built, with an unknown billing model, not investigated here. Worth a real spike if EVM gasless trading for Google sessions becomes a priority; not guessed at or half-built now.

**The bug this exposed.** `solanaTxIntent.ts`'s pre-sign firewall (§5) originally hard-required the transaction's fee payer to equal the user's own wallet — correct for every other Solana path, but it meant `signAndSendSponsoredSolanaStep` was calling the firewall with a transaction whose fee payer was deliberately the sponsor, not the user. Every sponsored trade failed this check, and the failure was swallowed one layer up into a generic "add more SOL" message — so a real, working sponsorship path looked, from the outside, like sponsorship simply didn't exist. Root-cause traced through `executeRelayQuote.ts`'s actual call sites, not guessed. Fixed by splitting the firewall into two independent checks instead of one field asked to mean both things: the fee payer must be the user *or* an explicitly-passed trusted sponsor (`expectedFeePayer`), and the user must independently still appear as a required signer of the transaction (`requiredSigners`, derived the same way `@solana/web3.js`'s own message compiler derives it) — so a sponsor covering the fee is never mistaken for the sponsor authorizing the trade. Full writeup: `docs/SOLANA_SPONSORSHIP_FIX.md`.

**Verification.** `scripts/verify-solana-fee-sponsor.mjs` (17 checks: 7 on the instruction rewrite, 10 on the cost-recovery math and the compute-budget helper — the network-dependent simulate-and-decide flow around them isn't testable offline by nature) and `scripts/verify-solana-tx-intent.mjs` (19 checks, including 4 regression cases reproducing the exact bug above) both pass. Live-deployed on `mango-api`'s Cloudflare Worker; end-to-end confirmation against a real funded sponsor wallet and a real previously-failing trade is the one remaining step (tracked separately, not blocked on anything documented here).

**Two fail-open gaps hardened, per an uploaded audit's MANGO-H02/H03 (verified against this exact file before acting, not taken on trust).** Both were previously WARNINGS, not blocks: (1) an unrecognized Solana transaction shape — `describeSolanaTransaction` returning `null` — used to warn "could not be inspected" and let signing proceed anyway, which is backwards for a wallet: an inability to verify a transaction is not evidence it's safe. (2) the four dangerous SPL instruction classes (Approve, ApproveChecked, SetAuthority, CloseAccount) — this file's own header already concluded "none of the three belongs in a swap route" when they were first added as warnings; that conclusion just hadn't been enforced yet. Both are now hard `SolanaIntentError` throws. Checked for real breakage risk before promoting, not just applied blindly: this app's own two Solana transaction sources were read directly — `executeRelayQuote.ts`'s cost-recovery addition only ever appends an SPL Transfer and, at most, an Associated-Token-Account Create (neither is one of the four), and this app requests Solana's native-SOL identifier from Relay, never WSOL, so there's no wrap/unwrap step of its own construction that would need a CloseAccount either. Tests updated to match (`scripts/verify-solana-tx-intent.mjs`, same 19 checks, now asserting blocks instead of warnings for these cases).

## 1b. Withdraw gas sponsorship — same infra, no cost recovery, by design

Withdraw (send-to-external-address, `ProfileScreen.tsx`) hit the same "0 native gas" wall trades already solve for: a user with, say, $4 of BNB and nothing else on that chain couldn't withdraw it. Fixed by reusing §1/§1a's already-built, already-tested sponsorship paths rather than building a third mechanism:

- **EVM**: `sendUsdc.ts`'s `sendEvmCashAsset` now takes a `useGaslessTrading` flag (threaded from `ProfileScreen.tsx`'s existing `gaslessTradingEnabled` preference, `gaslessTradingPrefs.ts`). When set and Pimlico is configured, it builds the same 7702 sponsored smart-account client as a trade would (`getSponsoredSmartAccountClient`/`getEip7702AuthorizationIfNeeded`, `smartAccount.ts`), with the same pre/post-broadcast discipline as everywhere else sponsorship is attempted: a `publicClient.call()` revert-check first (safe to catch broadly, nothing broadcasts from `.call()`), and only a narrow, specific regex match on known pre-broadcast bundler rejections (`invalid fields set on user operation`, `invalid useroperation`, an `AA` error code) is allowed to fall back to a plain transaction — any other failure after `sendTransaction()` propagates as a real error instead of risking a double-send of real funds.
- **Solana**: `sendSolanaUsdc` tries the normal direct send first; only on an `insufficient lamports` shortfall does it fall back to `executeRelayQuote.ts`'s own exported `signAndSendSponsoredSolanaStep` — the exact same fee-payer path a sponsored trade uses, via a minimal `SolanaTransactionSigner` wrapping the local `Keypair`. No new backend surface, no new signing code.
- **Deliberately no cost recovery on this path — a real, explicit product decision, not an oversight.** Every other sponsored path (trades, Convert — see below) recovers its real cost atomically, in the same transaction, before it ever reaches the user (§1's EVM paragraph, §1a's Solana paragraph). Withdraw does not: the withdrawal amount is exactly what the user typed, sponsorship is a pure cost to Mango on this path. Raised directly and the answer was explicit: cover it via some other revenue lever later, not by shaving the withdrawal itself — a user withdrawing $4 expects $4 to arrive, and building recovery in here would either under-deliver that or require a second "recovery fee" disclosure this flow doesn't have room for yet. Tracked as an open item, not silently absorbed.
- **Convert gets recovery for free, no new code.** Convert (`ConvertCashSheet.tsx`) already routes through the same `executeRelayQuote()` every trade uses, and — confirmed directly by grep — neither `sendRelayEvmStepSponsored` nor `signAndSendSponsoredSolanaStep` gates cost recovery on `waiveAppFee` or on which screen called them. So the moment Convert started passing `useGaslessTrading` through (the fix that unblocked its "insufficient gas" errors in the first place), it automatically inherited the exact same atomic recovery as any other trade. This is the one sponsorship surface in the app that's both free-to-use-gas and cost-recovering by construction; Withdraw is deliberately the one that isn't.

## 2. Stack, and matching mango-mobile's look

**Bare React Native (0.87.0, same version as mango-mobile) + TypeScript** — a real mobile app, not a web app. An earlier pass through this plan scaffolded Mango Pro as a Vite/React/Tailwind *web* build styled to look mobile-ish; that was a real misread of "mango pro should have mango mobile's look" and has been corrected — Mango Pro is mango-mobile's sibling app, running on the same bare-RN toolchain (Metro, not Vite; StyleSheet, not Tailwind; a screen-switch state machine, not react-router, same as mango-mobile's own `App.tsx`), not a website wearing mobile styling. `react-native-webview` replaces the `<iframe>` the earlier web scaffold used for the DexScreener chart embed; `react-native-svg` replaces inline SVG/lucide-react for icons — both already real dependencies of mango-mobile, ported for the same reason.

**Visual language**: per your explicit steer, Mango Pro should look and feel like **mango-mobile**, adapted for its different (token-first, not chain-first) flow. Concretely:
- `src/theme/palette.ts` is a byte-matched copy of mobile's own `src/theme/palette.js` — the monochrome black/white base with GAIN green/DANGER red/WARNING yellow reserved only for trading semantics is a deliberate, hard-won brand rule (the site's own history shows a flat accent color and a "LIME" color were both removed specifically because a flat single color breaks across light/dark themes).
- Layout follows mango-mobile's own conventions exactly, because it now runs on the same RN primitives: a bottom tab bar for primary navigation, card-based panels with rounded corners, the same pill/chip/button shapes.
- The "different operations" adaptation is mainly the home/search screen: instead of mobile's Wallet/Bridge/Swap/Launchpad tab bar built around chain-first actions, Mango Pro's primary tab is a token search — everything downstream (token detail, payment-asset picker, confirm, track) reuses the same card/panel visual language mobile already establishes.

## 3. Chain data, fees, and the routing engine — built inside this repo, carefully

Per your explicit instruction, this lives **inside `mango-pro`**, not as a separate published package — avoiding the operational overhead (and "confusion") of standing up and versioning a new repo before Mango Pro has a working product. The discipline that prevents this from becoming a fourth silently-drifting copy comes from structure and verification, not from extraction:

- **`src/core/chainData.ts`** — a single, carefully-written module for chain IDs, native-asset symbols, verified token addresses, and decimals — modeled directly on `mango-bridge.jsx/src/chainData.js` (confirmed to be the cleanest, dependency-free version of this data across all three repos), but written fresh for this repo with real values re-verified against the sources those files already cite (Circle's own USDC address list, etc.) rather than copy-pasted blind.
- **`src/core/fees.ts`** — fee wallet addresses and the `appFeeBps()` capping logic, same shape as `devFeeWallets.js`/the bot's `fees.ts`. Since this is the exact constant that silently drifted before, add a small `scripts/verify-fees.mjs` (mirroring the `verify-*.mjs` culture already established in `mango-mobile`'s `package.json`) that asserts the fee rate/cap are exactly what's documented in this plan, run in CI, so a future edit here can't silently change the effective rate without a visible, reviewed diff.
- **`src/core/router.ts`** — the routing decision engine, designed from the start as a **declarative, ordered rule table** (native-protocol routes like CCTP/OP-stack/Arbitrum-bridge/Wormhole preferred when available, falling through unconditionally to Relay) rather than the imperative if/else buried in `mango-bridge.jsx`'s `App.jsx` today. This makes it unit-testable in isolation from day one — a real advantage of building fresh here rather than porting the harder-to-extract version.
- If/when Mango Pro proves itself and there's a real appetite to retrofit the other three repos onto shared logic, extracting this `src/core/` folder into a published package at that point is a mechanical follow-up — but that's explicitly future work, not part of this plan.

## 3a. Settlement model: stay aggregated — don't pin to one chain

**This section previously recommended pinning all settlement to one chain (Base). That recommendation is retracted** — it was made before checking the closest real precedent, and the precedent says the opposite. Left here so the reasoning (and the correction) is on the record, not silently dropped.

**The finding.** FOMO — the funded, shipping app this whole plan treats as its closest real-world validation (§0) — publishes its own Relay case study, and it's specific: FOMO supports "trading across six blockchains — Solana, Base, BNB Chain, Monad, Ethereum, and Robinhood Chain — all from a single account with one cash balance," and this is exactly what "allows users to reliably trade into and out of the same stablecoin balance, making crosschain activity natural, not a conscious choice." That's the **aggregate model** — real balances spread across every chain the user has funds on, unified only in the display — which is the shape `usdcBalances.ts`/`TokenTradeScreen.tsx` already ships today. FOMO does not restrict deposits to one settlement chain, and Robinhood Chain — the exact "Relay sometimes has no quote" example this plan keeps citing — is one of their six aggregated chains, not a special case they route around.

**Why aggregation works without pinning.** Relay's own settlement mechanism is built for exactly this: a user's funds on the origin chain lock into a non-custodial Depository contract, and a solver who already holds liquidity on the destination chain fronts the output immediately, reimbursing itself from the locked origin funds once settlement is proven. That's what makes "spend from wherever your balance sits, land wherever you're trading" work as a single hop, without the app forcing everything through one chain first — and non-custody holds throughout, since the lock is a contract the user's own funds go into, not a Mango-controlled wallet.

**What this changes.** Pinning to Base wouldn't have delivered the "one Mango currency" feeling — that comes from Relay's solver network making any-chain-to-any-chain feel instant, not from restricting where deposits land. And pinning had a real, underweighted cost: it would have manufactured a **mandatory cross-chain sell leg** for every token not on the settlement chain, which is precisely the case (thin/new-chain tokens Relay can't quote) that's hardest to route — worse than today's shape, not better. It would also have required building the "sweep local stablecoin home via CCTP" apparatus described in the earlier version of this section, solving a fragmentation problem the aggregate model doesn't actually have: under aggregation, a stablecoin the fallback lands on some chain X *is* home — it's just counted as part of the one total, the same way any other chain's balance already is.

**So the real gap is routing depth, not settlement architecture.** The aggregate model + the disclosed consolidation-gap UI (Buy) it already has is the right shape. What's actually worth hardening:

- **Fallback coverage for thin chains/tokens** — the existing same-chain fallback (`fallbackDex.ts`/pump.fun-pumpswap, §8 Phase 2) is the real answer to "Relay has no quote," and it already keeps proceeds on the token's own chain rather than trying to force them anywhere else. Widening its coverage (more DEX routers, better Solana/pump.fun detection) is the lever that actually reduces how often a user sees the consolidation-gap message — not a settlement pin.
- **The consolidation-gap disclosure itself** stays exactly as built: honest, visible, never silently absorbed into a fabricated single number.
- **No CCTP sweep-home machinery, no settlement-chain migration CTA** — both were solving a problem this model doesn't have. Removed from scope.

This correction is independent of the §1 smart-account decision either way — it's about where funds are allowed to sit, not what signs for them.

## 4. Token-first search and discovery

No existing repo has anything resembling free-text, cross-chain token search — this is genuinely new build.

- **Primary source: DexScreener's public search endpoint** (`GET https://api.dexscreener.com/latest/dex/search?q=<query>`) — DexScreener is already the trusted cross-chain data source across the family (its chart embed is ported verbatim between the site and mobile, using its own ~30-chain slug taxonomy). Rank results by real USD liquidity, secondarily 24h volume — the same metric `dexScreenerChart.js` already trusts.
- **GeckoTerminal stays secondary**, for per-pool stat enrichment only — its own integration comments in this codebase describe it being hammered into 429s once already by exactly the "poll it often" pattern a search-as-you-type box risks repeating. This needs a **Phase 0 load spike** (below) before committing to it as sole search backbone.
- **Never silently merge same-named tokens across chains** — every result row shows chain + contract address explicitly, and known-malicious addresses get flagged via GoPlus's security API (same "fail open, never fabricate safety" contract already used in `goplusTokenSecurity.js`) run in parallel across visible results.
- **Caching, three tiers**: token metadata (decimals/symbol/name) cached forever (immutable once deployed); live market stats short-TTL (~30-60s); the raw search-query results themselves short-cached (~15-30s) specifically so typeahead doesn't hammer the search API.
- Once a token is picked, resolve the connected wallet's real balances across chains to offer as payment-asset options (default to the largest holding, let the user override) — this is what turns into the concrete `(originChainId, originCurrency)` pair a routing quote actually needs.

## 5. Security — port both existing patterns, they're complementary

- **Intent-firewall pattern** (from `mango-bridge.jsx/src/txIntentFirewall.js`): records what the user actually asked for at quote time, and asserts the router's actual response didn't deviate (wrong chain, inflated native value, oversized approval) before anything gets signed. Port this into `src/core/` — it's already pure/framework-agnostic. **The bound it enforces must be the literal bound already encoded into the Relay request** (see §7) — a firewall checking a number that was never actually submitted to the solver can flag a problem but can't be the thing that stops it; the two have to be the same number by construction, not independently computed and hopefully in agreement.
- **Calldata-decode confirm screen** (from `mango-mobile/src/browser/DappRequestModal.tsx`'s pattern): decode ERC-20 `approve`/`transfer`/`transferFrom` to surface the *real* spender/recipient hidden behind an innocuous top-level `to`, flag unlimited approvals, and check every decoded address (not just `to`) against GoPlus's live malicious-address API.
- These are genuinely complementary, not redundant (confirmed by the bot's own code comments contrasting its unattended custodial signing against the site's user-facing confirmation) — both gate the same confirm screen: quote received → intent-firewall assertion (silent, throws before confirm renders) → calldata-decode display (visible) → sign.
- **Smart-account-specific addition**: since UserOperations go through a third-party bundler/paymaster, add a check that the paymaster/bundler response's actual calldata matches the UserOperation Mango Pro built and signed intent for — the same "does the response match what we asked for" principle extended to the account-abstraction layer.
- **GoPlus alone isn't enough on Solana** — its Solana coverage is thinner than its EVM coverage, and Solana is exactly where meme-token volume concentrates. Pair it with a lightweight Solana-native check (mint/freeze authority still active, LP burned/locked, top-holder concentration) so the safety badge means the same thing on both chains, not just on EVM.

## 6. Gas abstraction, concretely (per the earlier discussion)

- **EVM destination chains**: smart account + paymaster sponsors gas outright, or lets it be paid in the token being received — this is the whole point of the account-abstraction choice in §1.
- **Solana destination**: app-sponsored fee-payer (§1) — near-zero cost, fully closes the gap.
- **Cross-chain settlement gas** (the solver's own destination-chain delivery transaction): expected to already be solver-paid as an inherent property of how Relay's intent-based routing works — confirm this holds for the specific routes Mango Pro uses in the Phase 0 spike, not assumed.

## 7. Execution reliability — a thin policy layer over Relay, not a parallel engine

Meme-token volatility makes "get a quote, then execute" an unsafe simplification on its own — real time passes between quote, user review, signature, and settlement, and price can move meaningfully in that window. This needs real design, but the design has to stay a **thin policy layer over Relay's own numbers**, not a second, independently-computed risk-scoring system sitting beside it — if Mango's own `minimumOutput` ever disagrees with what was actually submitted to the solver, the check becomes decorative: something that can *notice* a problem but never *stop* one, since the trade was already authorized under a different bound than the one being checked.

- **Encode the approved bound into the request itself.** Relay's quote already returns expiry, slippage, and impact data — the flow is: get a quote → derive `minimumOutput` from it → put that exact value into the actual Relay execution request (`EXACT_INPUT` with a hard minimum) → the intent-firewall (§5) checks the response against that same value. One number, one source of truth, not two computed separately that need to agree.
- **Drift-triggered re-quoting, not a wall-clock countdown.** A quote round-trip is already a few hundred milliseconds; a short fixed TTL (2-5s) just means near-continuous re-quoting and a number that visibly changes while someone's still reading it — worse UX, not better protection. Instead: watch for price drift beyond a threshold (basis points, tuned per asset class — wider for majors/stables, tighter for illiquid tokens) and silently re-quote in the background; only interrupt the user if a new quote would violate the `minimumOutput` they already approved. Keep one generous hard ceiling (~20s) as a backstop for the case where nothing else fires.
- **Idempotency has to be anchored on-chain, not in browser storage.** A local record (IndexedDB, etc.) only protects against double-submitting from the *same* device — it says nothing about a retry from a different tab, a different device, or after a crash. The real protection: a deterministic UserOperation nonce key derived from the execution's own ID (EVM), and a durable nonce account tied to the same intent (Solana) — a retry becomes inert by construction because the chain itself rejects the duplicate, rather than relying on the app remembering it already tried.
- **Solana: durable nonces, not "re-sign after the blockhash expires."** A normal recent-blockhash transaction expires in roughly a minute; losing a trade (or worse, asking someone to re-sign mid-launch) to that expiry is a bad, avoidable experience. A durable nonce account keeps a signed transaction valid indefinitely until actually used, so the app can keep rebroadcasting instead of asking for a new signature. Since the fee-payer is app-sponsored (§1/§6), that signing step is partial signing done by a real backend service — it sits on the critical path now and needs its own rate limits and abuse controls, not just "a helper function."
- **EVM: "replace," not "escalate."** A submitted UserOperation can't have its gas bumped in place — a stuck one gets resubmitted with the same nonce and higher fees, and exact replacement rules vary by bundler. Treat "submit → stall → replace → confirm" as an explicit test case in the Phase 0 provider spike, not something discovered for the first time in production. Evaluate EIP-7702 alongside counterfactual ERC-4337 in that same spike — it upgrades a plain wallet address in place rather than deploying a new counterfactual one, which sidesteps the "why is my address different here" confusion entirely, a real simplicity win if the tooling around it is mature enough.
- **A simple outcome log, from day one.** For every executed trade, record the quoted output against what was actually received, plus latency and route. This costs little to add now and is what turns "is this threshold about right" from a guess into an answer within the first couple of weeks of real trades.
- **What this deliberately is NOT, to keep Phase 1 shippable**: multi-RPC parallel broadcasting, a dynamically-weighted multi-factor route-scoring formula, and a granular state-machine UI beyond a few honest steps (quote secured → submitted → confirmed → delivered, with a plain "this is taking longer than expected" state rather than a silent spinner) are real, reasonable ideas — but they're Phase 2 polish once the core loop is proven, not launch requirements. The goal stated up front — simplicity and a smooth trading experience — is better served by a reliable, honestly-communicated basic loop than a more elaborate one shipped later.

## 8. Phased build order

**Phase 0 — spikes, no product code:**
- Evaluate and pick an account-abstraction provider (Pimlico vs. Alchemy Gas Manager vs. Biconomy vs. Particle Network, per §0) against real cost/reliability for the chains Mango Pro launches on; confirm counterfactual smart-account deployment (or an EIP-7702 upgrade, evaluated alongside it) and a real sponsored UserOperation round-trip on testnet.
- Explicitly test the EVM "stuck transaction" path: submit → stall → replace with the same nonce at higher fees → confirm. This is a real, different mechanism from "escalating" a transaction, and needs to be proven against the chosen bundler before Phase 1 relies on it.
- Prove a durable-nonce Solana flow end-to-end (create nonce account → sign against it → rebroadcast after a delay) rather than assuming recent-blockhash transactions are good enough for volatile-token trades.
- DexScreener search-endpoint load test at realistic typeahead volume — decide if a paid tier or a static fallback list is needed.
- Confirm Relay's quote API requires a concrete resolved origin per call (it does, per `relaybridge.js`'s `getRelayQuote` signature) — so "auto-suggest best payment asset" means Mango Pro fanning out parallel quote requests across the user's held assets itself, not a capability Relay hands you for free. Scope this fan-out cost before promising an "auto-pick" UX.

**Phase 1 — MVP core loop (demoable):**
- Embedded smart-account wallet (EVM) + standard keypair wallet (Solana), passkey-gated root key + spend-capped session keys (§1), onboarding flow modeled on mobile's.
- DexScreener-backed token search with GoPlus badges (+ the Solana-native check from §5) and a token detail page.
- Manual payment-asset picker from real connected balances (defer auto-suggest to later).
- Relay-only routing for v1 (defer CCTP/native-bridge special-casing — Relay alone proves the full loop; native routes are a pure optimization layered on after). **One real exception, not a hypothetical**: mobile already hit and fixed this exact gap for same-chain EVM swaps — Relay's solver network sometimes has no indexed route for a thin/new token that a direct DEX router or an aggregator can still find, so Relay-only there means some genuinely tradeable tokens silently fail to quote. Same-chain swaps are the common case in Mango Pro's own token-first flow (payment asset already on the target chain), not an edge case — see Phase 2 below for the proven fix to carry over, deferred only because it's real added engineering, not because Relay-only is believed sufficient there.
- The thin execution-reliability policy layer from §7: bound encoded directly into the Relay request, drift-triggered re-quoting with a hard ceiling, on-chain idempotency (deterministic nonce/durable nonce), UserOp replacement plumbing proven in Phase 0.
- The ported intent-firewall + calldata-decode confirm screen — non-negotiable, not deferred, and cheap since both are ports of existing code rather than new engineering.
- Honest, basic execution states (quote secured → submitted → confirmed → delivered, plus a plain "taking longer than expected" state) and a minimal portfolio view. The outcome log from §7 starts here too — cheap to add, valuable almost immediately.

**Phase 2 — routing quality:**
- Add back CCTP/OP-stack/Arbitrum/Wormhole native routes into `src/core/router.ts`'s rule table now that it's a testable module.
- Add a scoring layer for the Relay bucket specifically (net amount after fee, ETA, risk discount) since Relay's own internal DEX/solver choice is otherwise a black box — and by this point the outcome log from §7 has real data to tune the weights against, rather than guessed ones.
- Multi-RPC parallel broadcast for Solana and a richer execution-state UI, now that the basic loop and its failure paths are proven in production (deliberately deferred from Phase 1, per §7).
- **Same-chain swap fallback — port the proven architecture from mango-mobile's `src/bridge/fallbackDex.js`, not a fresh design.** Only fires when Relay fails twice (including a 0%-fee retry) — Relay stays the default path, this is a safety net for what it can't route:
  - **EVM**: try direct on-chain routers first (Uniswap V4 → Uniswap V3 → SushiSwap V2 → PancakeSwap V3 — no API key, no backend dependency, and the only path that works on chains with no aggregator coverage), then generic aggregators (1inch, 0x, OKX, KyberSwap) through a backend quote proxy. Quote all of them in parallel and take the **highest output**, not first success — mobile's own history includes a real bug from taking the first provider that answered instead.
  - **Solana — two genuinely different problems, not one**: (a) tokens with a live pump.fun bonding curve or a graduated PumpSwap pool need a **direct pump.fun/PumpSwap integration**, because Relay's Jupiter-based routing specifically mis-costs those trades (mobile hit a live "insufficient lamports" failure) — check bonding-curve/pool presence and route there ahead of Relay for any Launchpad-originated token. (b) ordinary Solana swaps with no pump.fun presence still have **no fallback anywhere in this app family** if Relay's route is bad — Relay's own routing already goes through Jupiter internally, so a "just add Jupiter" fix doesn't exist to copy; a genuinely separate direct Jupiter integration is real, unbuilt engineering here, not a port.

**Phase 3 — polish:**
- Auto-suggest-best-payment-asset upgrade (using the Phase 0 fan-out spike's findings).
- Richer history/portfolio, any deferred UX polish.

**Explicitly out of v1** (per the product spec's own stated MVP boundaries): derivatives, complex trading terminals, chain support beyond Relay+CCTP+OP-stack, any custodial fallback path.

## 9. Roadmap: aggregated-balance Buy/Sell (multi-leg execution) — designed, deliberately not built yet

**Status: documented for next session, not started.** Raised directly: the app has come a long way on real sponsorship/safety work this session (§1, §1a, §1b), and the honest call is that this is a genuinely new execution surface, not a tweak to something proven — better to land it deliberately next session than rush it in alongside everything else already shipped today.

**The gap this closes.** §3a already chose the aggregate balance model (real funds spread across chains, unified only in display) over pinning to one settlement chain — and that's the right call. But today, aggregation only helps *display*: a user with $1.50 on Base, $4.78 on Solana, and $2.83 on BNB still can't actually spend that as one $9.11 Buy — each chain's balance can only fund a trade whose origin is that same chain, because Relay's quote API takes exactly one `(originChainId, originCurrency)` pair per call (confirmed via `relaybridge.js`'s `getRelayQuote` signature, §8 Phase 0's own note). The FOMO reference product markets a single spendable balance across six chains; matching that claim for real — not just in the balance display — needs an actual multi-leg planner, not just aggregation math.

**What this is not, stated up front:** this is unrelated to, and does not reopen, the withdrawal fan-out question already explicitly rejected earlier this session (§1b) — sending a user's funds to one destination address across multiple chains without knowing whether that address is single-network (e.g. a CEX deposit address) risks real, unrecoverable loss, and stays rejected. A Buy/Sell leg here always settles through Relay's own solver into the *user's own* destination (their own wallet, or the token being bought) — never a blind fan-out to a third-party address. The two features share no code path and should not share a mental model.

**No one gets true atomicity here, not even FOMO — the design has to be honest about that, not paper over it with a single spinner.** Once leg 1 lands on-chain, there's no rollback if leg 2 fails; this is an orchestration/UI-layer illusion of "one trade" built from N genuinely independent transactions, the same reality §3a already established for cross-chain settlement generally. Five concrete pieces, all needed together:

1. **Leg selection.** Given a target spend amount, greedily pick chains largest-balance-first until the target is covered. Skip any chain where bridge+gas cost would eat more than ~15-20% of that slice's value, and disclose the skip — the same honest-disclosure pattern the consolidation-gap message already uses today (§3a), not a new UX language.
2. **Reuse the existing pipeline per leg, don't build a new one.** Each leg is the same `getRelayQuote` → intent-firewall (§5) → `executeRelayQuote()` call already proven for every other trade, just invoked N times with a different origin. Zero new security surface, zero new trust boundary — the multi-leg planner's only new job is sequencing and bookkeeping around calls that are each individually already safe.
3. **One combined price bound, computed before leg 1 fires.** Derive a single `minimumOutput` across the whole multi-leg spend up front (§7's "encode the approved bound into the request itself" principle, extended from one call to N) — so a token moving while leg 3 is still pending can't silently hand the user a worse deal than the one they approved for the whole trade.
4. **Honest partial-failure state, never silent rollback (there is none).** E.g. "2 of 3 succeeded — you received $9.63 of TOKEN; $2.83 on BNB wasn't converted and is still sitting there." The outcome log from §7 needs to record **per-leg**, not per-trade, so a partial failure is legible in the data, not just in the moment.
5. **Sequential execution with real per-leg progress, not one spinner.** "Leg 2 of 3: converting $2.83 from BNB…" — matches §7's own "no silent spinner" execution-state principle, extended across legs instead of within one.

**Scope note:** this is a real, new execution planner — sequencing, combined-bound math, per-leg outcome logging, and a genuinely new confirm/progress UI — not a small extension of `executeRelayQuote()`. Sizing and sequencing this properly is next session's work; nothing here should be started piecemeal ahead of that.

## Verification approach

- `src/core/` module gets its own unit tests (chain data shape, fee math, router rule-table resolution) runnable via `npm test`/a `verify` script, mirroring the existing repos' own verification culture rather than inventing a new one.
- Phase 0 spikes are explicitly "prove it before building on it" — the account-abstraction sponsored-transaction round-trip and the search-endpoint load test both need a real, observed pass/fail before Phase 1 work depends on them.
- Before shipping Phase 1, run the same class of checks already established elsewhere in this session: typecheck clean, lint clean, and a manual walkthrough of the full search → pick payment asset → quote → confirm (intent-firewall + calldata-decode) → sign → track loop end-to-end on testnet.
